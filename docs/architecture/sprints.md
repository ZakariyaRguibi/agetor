# Native sprints

The acceptance contract is in `docs/plans/sprints.md`. `src/shared/sprint.ts` validates editable inputs and implements the pure eligibility/shipping gates. `082_sprints.sql` is additive; existing tasks/pipelines are unchanged. `sprint-store.ts` stores versioned sprint payloads with SQLite transactions and optimistic revision checks. No transaction is held across external work. Profile contents participate in batch hashes, not merely their IDs. Requirement revisions clear approvals and review evidence while preserving repair counts.

## Local HTTP contract

All routes use the existing bearer-token/CORS/boot-gate middleware. `GET /sprints` returns `Sprint[]`; `GET /sprints/:id` returns one `Sprint`. The ordinary CLI token can read these records.

All mutations require the desktop master token. `POST /sprints` takes `SprintInput` and returns the new `Sprint` (201). `PATCH /sprints/:id` takes `{revision,input}`. `POST /sprints/:id/actions` takes `{revision,action}`. Actions are `setup-agents`, `plan`, `approve-spec`, `tickets`, `approve-batch`, `run`, `pause` and `resume`. Unknown actions fail closed. Runtime state, approval hashes and attempt counters are never accepted from client bodies. Success responses contain the full revised `Sprint`, including its next revision. Invalid inputs return 400; stale revisions/state conflicts return 409; missing records return 404. Action/preflight errors use 409. Agents cannot approve themselves using their readable CLI credentials.

The authoritative payload types/validation live in `src/shared/sprint.ts`. Specifications and selected prerequisite-closed ticket batches have separate approvals. Loading a draft does not execute work or publish code. Subscription-only confirmation and explicit required CI names are required for executable batch approval.

Saving a draft never requests planning or ticket generation. Completed generation records remain complete. An edit cancels a queued generation request and keeps its attempt ledger. Saving a paused sprint that has not started implementation returns it to draft for explicit approvals. Ticket generation requires approval of the current specification both when requested and when its result is imported.

## Execution and ownership

`sprint-controller.ts` starts a three-second supervisor only in the core that owns the API port, after native orphan and pipeline reconciliation. It uses existing native tasks/profiles/events/worktrees. It does not create another daemon or bypass the app's boot ownership. `sprint-runner.ts` schedules prerequisites, polls native workers, checks code directly, requires independent review and integrates passing candidates. Each ticket has an isolated root worktree; separate execution/review tasks share only that ticket's workspace. Existing reviewed prerequisite commits are merged into a clean reused root before its next implementation. Conflicts or uncommitted work needing new prerequisites stop for resolution.

Migration 083 journals direct command launches with PID and kernel birth time. Recovery terminates only a matching identified orphan process group. Unknown identity checkpoints for human inspection instead of starting a duplicate. Migration 084 binds native tasks to a sprint and purpose. Ordinary task starts, edits, deletes, profile detaches and free-form follow-ups are refused for managed tasks. `Task.sprintId` and `GlobalEvent.sprintId` are derived read-only metadata; deterministic internal titles support recovery, while the API presents readable names. Existing native answer cards remain available.

One in-process lock serializes each sprint. Launch reservations bound simultaneous preflights, and live-task/workspace checks prevent a replacement overlapping a cancellation still draining. Source checks, integration and review only proceed after workers quiesce. Native task/run IDs, candidate SHAs, attempts, repairs and cooldowns are persisted. Requirement edits revoke approval/evidence, preserve retired ticket budgets and advance internal job identities so old completed jobs cannot satisfy a new revision.

## Verification protocol and limits

Models return exactly one unfenced, non-inline `<sprint-result>{JSON}</sprint-result>` block. Generation imports validated specification/tickets/checks into the draft; implementation may request approval with `requiresApproval:true`. Review requires `verdict:"PASS"`, the exact `candidate` SHA and an empty `findings` array. Exit zero or an ordinary successful native task is insufficient. Output replay is bounded and limited to the current run's main assistant stream.

Direct checks use argv arrays through `coreSpawn`/`childEnv`, no implicit shell, `CI=true`, bounded output and process-group cancellation. The approved spec and ticket Markdown must match exactly before verification. The versioned ticket packet preserves all backlog items, labels execution selection, and final review receives only the selected tickets. Regeneration retains existing identifiers omitted from model output. Checks cannot modify source undetected: staged tree identity is compared before/after. Passing changes are committed before read-only review. A changed approved packet is a human blocker, not an automatic repair. At most three model agents, twenty minutes per attempt and three repairs per ticket (including fallbacks) apply. Verification, documentation and final repairs are also bounded. Reported quota resets take precedence; absent a reset, backoff grows from five minutes to six hours. Pauses and counters survive a new core.

Managed Codex routes force ChatGPT login and the OpenAI provider, and disable multi-agent delegation. OpenCode pins both model and small model to the configured Go DeepSeek route, standalone execution and no task delegation. Claude disables Agent/Task tools. CLI extra argument overrides are ignored for managed jobs. Billing preflights reject known API/cloud overrides and unsupported roles; account-side overage disabling remains explicit user attestation. Existing non-sprint launches keep their settings. These controls do not sandbox arbitrary repository programs or inspect provider account spending switches.

## Release and architecture decisions

`sprint-release.ts` advances documentation, whole-sprint checks, current-main integration, independent final review, PR/CI and squash merge as persisted native jobs. Documentation edits are restricted to Markdown and require nonempty README, CHANGELOG and sprint report. Approved packet changes stop for review. UI deltas require an approved browser command. New remote main content invalidates final check/review evidence; conflicts are not resolved automatically. All selected tickets must remain passed on their reviewed SHAs.

**Decision: require server-side base freshness.** A head-SHA lease alone cannot prevent main changing between the final local check and GitHub merge. Automatic shipping therefore requires classic strict required-check protection with administrator enforcement, checked before models start and before merge. Rulesets-only protection is currently unsupported; do not silently use admin bypass. No repository policy is changed automatically. The alternative of best-effort local base polling was rejected because it cannot close this race.

One stable branch identifies the PR across recovery. Existing closed/merged PRs are reconciled rather than duplicated. CI requires exact configured names and successful completed states on the verified head; pending/missing/skipped states wait, with a thirty-second release cooldown. Red checks enter bounded repair and fresh review. `--match-head-commit` guards squash merge. Recovery confirms the merge on remote main before fast-forwarding the clean original checkout. No deployment occurs. Disabling shipping completes on the local sprint branch.

Native notifications use the existing notifier with persisted deduplication; routine managed task notifications are suppressed. Existing always-on infrastructure can host the supervisor in a packaged build. OS sleep is permitted, not inhibited. See [usage](../sprints.md) and [qualification](../qa/native-sprints.md) for operational limitations and actual evidence.

Local installation uses `AGETOR_LOCAL_BUILD=1` for stable-channel data compatibility with ad-hoc signing and no notarization. Its release feed is empty; the updater refuses both checking/applying an empty feed so an upstream bundle cannot overwrite fork features. Ordinary release builds retain their existing feed/signing settings. The local ad-hoc build cannot enable the Developer-ID-gated login-item host.
